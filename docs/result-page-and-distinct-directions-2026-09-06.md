# 结果页面升级兼容与三种配色

## 页面异常不代表照片处理失败

用户报告 `result-count` 为 null 的任务 `065bddd2-0083-418a-9793-2df7ffac62ac` 在后台已是 ready，三张成片均已保存。已安装 HTML 包含这个元素；报错说明新脚本运行在缺少新元素的文档上。旧页面缓存与新版脚本混用是可复现的触发条件。

修复后，脚本兼容旧标题并补齐交付说明元素。静态页面及脚本返回 `Cache-Control: no-store`，桌面入口 URL 随 HTML、JavaScript 或 CSS 内容变化，避开升级前遗留的 WebKit 文档缓存。页面异常发生在 ready 任务时，显示“成片已完成，页面未能显示”及“重新打开成片”，重新读取既有任务，不再次调用处理接口。

当前任务记入本地存储和 URL；旧版本首次升级可读取最近任务，用户点“再来一张”后仍回到上传页。读取最近任务不修改照片、任务或反馈。

`scripts/check_result_page.py` 已在 macOS WebKit 上使用运行中应用提供的真实图片验证：旧 HTML 缺失两处元素、新脚本显示三张图片；仅交付 C 时正确显示数量且不能选撤下的 A/B；模拟页面异常后重新打开成片；新版页面恢复记录；主动重置后保持上传页。全过程没有处理或反馈 POST 请求。

## 方案为什么曾经很接近

- 城市原片主要呈青色，很多模型配方却只显著修改蓝色，对实际主色影响很小。
- `mean_luma < .10` 被当成夜景条件，把低调白天照片的 C 分配到同样保守的暗调方向。
- 银灰建筑与暖调方案的关键颜色能够被模型的显式零值清空；方案标题不一定对应可见配色。
- 相似方案的重试主要靠 B 压暗、C 提亮；B 在暗片上反复触发暗部裁切，只能退回相近的旧版本。

现在保留各自方案的基本配色：A 自然；建筑 B 收敛蓝青成银灰，其余场景 B 使用冷暖光或橄榄绿；C 以暖中间调和柔和亮部形成胶片氛围。青色占比高时实际修改 aqua，模型继续设计本图的明暗和局部关系。低调 B 保留暗部余量，相似重试沿自身配色调整，保留已通过检查的明暗与蒙版曝光。默认候选选择目标由平均 Lab 距离 2.8 改为 5.0；这不是审美分数，仍分别检查裁切、饱和度和可确认的视觉损坏。
